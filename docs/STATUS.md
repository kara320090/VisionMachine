# 현재 구현 상태

## 2026-11-13 아두이노 센서 4종 인계 — 현재 업로드 v0.2.0

- 사용자 요청에 따라 아두이노 쪽만 진행했다. Android 앱 소스 수정·앱 빌드 산출물 배포·Play 작업은 수행하지 않았다. UNO R4의 SEN0308 A0 ADC·SEN0334 온습도에 SEN0364 광학·SEN0206 표면온도 읽기를 추가했다. 같은 조립·배선에서 PC USB 확장 응답을 받았다.
- 기존 3필드 요청과 `basic`은 확장 키 없는 기존 응답을 유지한다. 명시적인 `sensor_profile=extended` 요청에만 버전이 있는 `extensions`를 추가한다. Python 원본 계약·요청/응답 JSON Schema·OpenAPI를 갱신했고, 확장 없는 모델의 직렬화에도 임의 `extensions:null` 키를 넣지 않는다.
- 광학은 SMUX 설정 쓰기·읽기 대조, 준비 대기 상한, 검사한 데이터 블록 읽기로 순차 노출 2회의 원시값 12개를 보낸다. gain 16×·ATIME 29·ASTEP 599·노출당 50.04ms·주변광/LED off·포화 상태를 기록한다. 매 요청 설정값을 확인하고 초기화·읽기 실패 후 재설정한다. 라이브러리의 무한 대기/오류를 버리는 캐시 읽기는 사용하지 않는다.
- MLX90614는 대상·센서 자체 온도 레지스터와 방사율 EEPROM을 읽고 SMBus PEC CRC-8·오류 비트를 검사한다. 실패는 `null`·오류이며 다른 정상 센서의 값을 지우지 않는다. EEPROM 쓰기나 임의 교정값 추가는 하지 않았다.
- 최종 빌드·업로드 성공: flash 69,312 bytes, 전역 RAM 6,100 bytes. Arduino CLI 1.6.0, Renesas UNO core 1.6.0, SHT31 2.2.2, BusIO 1.17.4, AS7341 1.4.1. core 내부 경고가 있으며 이 스케치의 빌드를 막지 않았다.
- 최종 보드의 실제 USB 패킷 16개(확장 실측 5·기본 1·기존 USB 회귀 10)를 원본 계약으로 검증했다. 확장 5회는 광학·표면온도와 기본값을 받고 오류가 없었으며 최대 프레임 1,018 bytes였다. 잘못된 요청은 계측값을 모두 `null`로 반환하고 초과 줄·분할 수신에서 복구했다.
- 별도의 임시 진단 빌드에서 확장 센서를 실제 응답 없는 주소 0x38·0x59로 지정한 오류 시험 3회(extended/basic/extended)를 수행했다. 확장 요청 2회는 두 센서만 `null`·오류이고 SHT31 값은 유지됐으며 기본 요청은 기존 형식이었다. 이는 물리적인 센서 분리·재연결 시험이 아니다. 시험 뒤 정상 주소를 쓰는 진단 출력 없는 v0.2.0을 복원했다.
- `scripts/check.py`의 pytest 82건·계약·OpenAPI·manifest·HTTP 점검, MSVC의 요청 디코더 검사 282개·공식 Melexis 예제 기반 PEC/온도 검사 5개가 통과했다. 실제 로그·장치 식별자는 공개 Git 밖에 보관한다.
- 사용자 결정에 따라 흙·밝기·대상 변화, 센서 물리 분리/재연결, 휴대폰 USB 전원·통신 시험은 나중에 Android 연결 단계에서 수행한다. 토양은 원시 ADC이며 프로브 연결·수분율 교정 완료로 쓰지 않는다. 요청·단위·오류·휴대폰 연결 절차는 [ARDUINO_PHONE_HANDOFF](ARDUINO_PHONE_HANDOFF.md), PC 확인 명령은 `firmware/Measure-UsbSensors.ps1`을 따른다.

## 2026-11-13 공유 I2C 탐색 간격 수정 — 현재 업로드 v0.1.2

- 사용자 확인상 센서가 모두 연결된 상태에서 진단 주소 응답은 광학 `0x39`, 온습도 `0x45`, 표면온도 `0x5A`였다. 단독 라이브러리·계측 클래스·진단 출력을 넣은 전체 펌웨어는 온습도를 읽었지만 진단 출력 없는 v0.1.1은 초기화에 실패했다. 캐시를 비운 빌드도 기존 바이너리와 SHA-256이 같아 캐시 차이로 설명하지 않는다.
- 주소 탐색 직후 1ms 간격을 두는 수정본 `uno-r4-0.1.2`는 전체 연결에서 정상 온습도를 반환했다. 동일 배선에서 v0.1.1을 다시 올린 3회는 `sht31_disconnected`, v0.1.2로 복원한 3회는 오류 없는 유효 온습도 응답이었다. 이 실물 구성의 연속 탐색 동작을 개선한 것으로 기록하며 core 결함이나 모든 전원·배선 조건의 통과로 일반화하지 않는다.
- v0.1.2의 실제 USB 응답 10개를 계약으로 검증했다. 정상·초과 줄 복구·분할 요청 3개는 유효 온습도를 받았고 잘못된 요청 7개는 계측값을 모두 `null`로 반환했다. 재업로드 비교 후 추가 정상 3회까지 총 6회 유효 온습도를 확인했다. 원시 로그와 장치 식별자는 공개 Git 밖에 보관한다.
- UNO R4 clean build 성공: flash 64,456 bytes, 전역 RAM 6,056 bytes. 요청 디코더 275개 검사와 `scripts/check.py`의 pytest 61건·계약·OpenAPI·manifest·HTTP 점검을 통과했다. v0.1.1 코드 커밋 `54f6f04`의 Windows/Linux Python CI와 Android 빌드·lint도 성공했다.
- 현재 보드에는 진단 출력이 없는 v0.1.2가 올라가 있다. 토양은 ADC 원시값이며 보정 수분율이 아니다. 광학·표면온도는 주소 응답 확인에 그치고 읽기 코드·계약, Android 실제 USB 연결은 추가 구현 대상이다.

## 2026-11-13 펌웨어 코드 검토·수정

- 기존 코드는 요청의 UUID만 찾아 버전·메시지 종류·JSON 구문을 검사하지 않았다. `MeasureRequestDecoder`로 세 ASCII 문자열 필드·소문자 UUID·구문·중복·추가 필드를 검사하도록 수정했다. 요청 규격과 응답 계약 0.1.0은 유지하고 펌웨어 버전은 `uno-r4-0.1.1`로 구분한다.
- 초과 길이 줄이 USB 조각 사이에 나뉘면 나머지를 새 요청으로 읽던 문제를 수정했다. 초과 오류를 한 번 내고 다음 LF까지 폐기한다. SHT31의 온도·습도는 두 번 따로 측정하던 것을 `readBoth()` 한 프레임으로 변경했다.
- Windows MSVC로 실제 요청 디코더 회귀검사 275개가 통과했다. UNO R4 빌드는 flash 64,440 bytes, 전역 RAM 6,056 bytes로 성공했으며 기존 Wire core 경고가 있다. Linux CI에 요청 디코더 검사를 추가했다.
- `scripts/check.py`의 pytest 61건, 계약·OpenAPI 동기화, manifest·실제 localhost HTTP 검사가 통과했다. 수정본 업로드 후 정상 요청·종류/버전 오류·누락·중복·잘못된 구문·초과 줄 폐기/복구·분할 수신을 실제 USB 응답 10개로 확인했고 원본 `SensorPacket` 계약 검증을 통과했다. 잘못된 요청은 계측값을 모두 `null`로 반환했다.
- 앞선 SHT31 단독 연결에서는 수정 전 펌웨어의 실제 USB 요청 3회가 유효 온습도와 오류 없는 응답을 반환했다. 이후 코드 검토 시점의 연결에서는 온습도가 다시 감지되지 않았다. 배선을 유지한 이전 버전 3회·수정 버전 3회 비교 모두 `sht31_disconnected`였으며, 마지막에 수정본을 복원했다. 수정본의 `readBoth()` 유효 온습도 수신은 이 연결 상태에서 확인하지 못했다. 실제 로그·원시값·장치 식별자는 공개 Git에서 제외한다.
- 토양 원시값 수신은 프로브 연결·수분 교정 검증이 아니다. 광학·표면온도 읽기와 Android USB 권한·직렬 포트 연결은 구현되지 않은 기능이다. 이번 요청 파서·측정 수정으로 해당 기능이 추가됐다고 기록하지 않는다.

## 2026-11-05 Android 사진 점검 동반 화면

사용자 요청으로 캡스톤 데스크톱 RGB 모델과 사진 분석·기록 UI를 Android 내부 테스트용 동반 경로에 연결했다. 기존 촬영·원본 저장·디버그 loopback 업로드·USB 패킷 계약은 보존했다. 센서·서버 통합 진단의 구현 상태는 이 작업으로 바뀌지 않는다.

- 런처 `AnalysisActivity`: 최대 8장 JPEG/PNG 선택, 첫 사진 분석, 선택 사진 일괄 분석, 사진 변경 시 현재 결과 초기화, 누적 기록 200건, CSV 내보내기. 기존 `MainActivity` 촬영 화면으로 이동할 수 있다.
- 실제 EfficientNet-B0 C_seed42 모델의 ONNX opset 17/softmax 2출력을 ONNX Runtime Android 1.31.1 CPU로 실행한다. 모델 카드와 SHA-256 검증을 제공하며 모델 가중치·실제 예시 사진·시험 정답·서명키·빌드 산출물은 공개 Git에서 제외한다.
- EXIF 8방향, PIL BICUBIC/중앙 크롭/정규화를 재현했다. 실제 현장 정확도나 재배 문제의 원인·보정된 진단 확률은 주장하지 않는다. 자세한 범위·모델 준비는 [ANDROID_RGB](ANDROID_RGB.md).
- Windows JDK 21.0.13(소스 타깃 17), SDK/target 36, Gradle 8.11.1/AGP 8.10.1에서 `assembleDebug`, `lintDebug` 통과(오류 0, 기존 스타일·의존성 안내 경고 14개).
- `testDebugUnitTest`: 합성 사진 5개 크기의 전처리 픽셀 해시가 Pillow와 동일(3000×4000 포함). Android API 37.1/16KB x86_64 에뮬레이터 `connectedDebugAndroidTest` 18개 통과/skip 0: 기존 촬영·서버·센서 파서 14개와 새 실제 RGB 모델·EXIF·12MP·사진 선택/초기화/일괄/기록 시험 4개. 추가 화면 기동·PixelCopy 렌더 시험 1개 통과.
- PC PyTorch→ONNX 변환은 보관 예시 8장에서 출력 최대 절대 차이 6.26e-7 미만, Android 실제 PNG 입력 출력은 PC 기준과 각 1e-5 이내로 일치했다. 이 비교는 변환·실행 동등성 시험이며 독립 성능 평가가 아니다. APK의 4 ABI 네이티브 라이브러리 12개 PT_LOAD가 모두 16KB 정렬이다.

아래 초기 구현 설명과 날짜별 기록은 이전 이력이다. 서버 모델 연결·실휴대폰/실센서 통합시험 완료를 의미하지 않는다.

## 이 패키지에 구현한 것
- 공통 계약 Python 모델과 생성 JSON Schema, 명시된 합성 예제.
- 서버 GET /healthz, GET /v1/capabilities, POST /v1/dev/validate-inspection.
- 모델 미탑재를 반환하는 ML 인터페이스(실제 추론 없음).
- CSV manifest의 필수값·경로·형식·중복 ID·그룹별 split 누수 검사.
- 선택적 `--image-root` 검사로 로컬 이미지의 존재, 루트 밖 심볼릭 링크, 실제 SHA-256 불일치 확인. 이미지 디코딩·라벨 검증은 아직 없음.
- 로컬 SQLite 초기화 CLI, 저장 경로 설정, 설치 패키지에 포함하는 SQL. 재실행 시 데이터 보존, 외래키, 알 수 없는 DB 거부, 실패 롤백 시험.
- 로컬 전용 실제 JPEG/PNG multipart 업로드·파일/SQLite 저장·검사 단건 조회. 사진 해시·디코딩·바이트/픽셀 상한, 재시도 200·충돌 409, 재시작 조회를 검증함.
- 실제 구현 API에서 생성한 OpenAPI, JSON Schema 동기화 검사, 실제 localhost HTTP smoke.
- Android Kotlin/Compose 프로젝트와 Gradle wrapper, 기존 카메라 앱으로 원본 JPEG를 앱 전용 파일에 저장하고 로컬 목록으로 표시하는 첫 APK. 디버그 앱의 loopback multipart 전송·수동 재시도·분석 대기 표시까지 구현. 실기기 촬영 왕복은 미검증.
- `scripts/check.py` 단일 검사 명령, Linux/Windows GitHub Actions 구성.
